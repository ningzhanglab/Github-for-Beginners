Learn GitHub by following one small project

Watch Mia keep her research notes in GitHub, from creating the project to working with a coauthor and an AI assistant. Every step shows what happens in all three places, so you can see exactly what changed and where.

Your folderThe files on Mia’s computer. She edits them with her usual editor.
GitHub DesktopThe free app that shows what changed, saves checkpoints, and syncs.
GitHub.comThe online copy, where people review and accept changes.

In every step, the place where you act is highlighted, and anything that just changed is marked like this. Lines that were added show + in green, removed lines − in red.

Mia That’s you: a researcher writing notes for a small wage study

Sam Mia’s coauthor, who joins in part 2

An AI assistant Helps in part 3, and makes one mistake

Before you start: get a free account and the app (5 minutes)
  1. Create a free account at github.com/signup.
  2. Download GitHub Desktop for Mac or Windows, install it, and open it.
  3. Click Sign in to GitHub.com on the welcome screen. (Later: GitHub Desktop → Settings… → Accounts on Mac, File → Options… → Accounts on Windows.)

You never need to type commands. Everything is buttons.

Start the story 16 steps, about 30 minutes to read. Steps 1 to 5 are all you need for personal work.

Part 1: On your own

Create a project, save checkpoints, and put it online. This is all you need for personal work.

1

Step 1 of 16

Create a project

Mia starts a project called wage-study. GitHub calls a project a repository: a folder that remembers its history.

Do this, in GitHub Desktop

  1. In GitHub Desktop choose File → New repository…
  2. Name: wage-study
  3. Tick Initialize this repository with a README
  4. Click Create repository

What changed: A new folder appears on her computer. Nothing is online yet.

2

Step 2 of 16

Write a note

Mia writes her first finding in a new file, notes.md, using her usual text editor.

Do this, in your folder

  1. In Desktop choose Repository → Show in Finder (Mac) or Show in Explorer (Windows)
  2. Create notes.md in that folder, type the note, and save

What changed: GitHub Desktop notices the saved file by itself and lists it under Changes, with new lines in green.

3

Step 3 of 16

Commit: save a checkpoint

Mia saves a named checkpoint, called a commit, so she can always come back to this version.

Do this, in GitHub Desktop

  1. In the Summary box type Add first note
  2. Click Commit to main

What changed: The checkpoint appears in History. It is saved on her computer only: GitHub.com still has nothing.

Watch out: Commit is not the same as uploading. Until she publishes or pushes, nobody else can see it.

4

Step 4 of 16

Publish to GitHub.com

Mia puts the project online, so it’s backed up and she can share it later.

Do this, in GitHub.com

  1. Click Publish repository in the top bar
  2. Keep Keep this code private ticked
  3. Click Publish repository

What changed: GitHub.com now has the same files and checkpoints. The Desktop button changes to Fetch origin.

5

Step 5 of 16

Edit, commit, push: the everyday routine

The next day Mia adds a second finding. She repeats the routine she’ll use every day.

Do this, in GitHub Desktop

  1. Edit notes.md and save
  2. Check Changes
  3. Commit with Summary Add wage change
  4. Click Push origin to upload

What changed: Edit, commit, push. Now her folder, Desktop and GitHub.com all match.

Part 2: With a coauthor

Get someone else’s changes, and propose your own for review.

6

Step 6 of 16

A coauthor changes the online copy

Sam does this

Mia invites Sam (Settings → Collaborators → Add people on GitHub.com). Sam notices that 5.0% to 4.5% is a fall of 0.5 percentage points, and fixes the line directly on GitHub.com.

Do this, in GitHub.com

  1. Nothing for Mia to do yet. Sam edits and commits on the website

What changed: GitHub.com now has Sam’s fix, but Mia’s folder still has the old line. Her computer does not update by itself.

7

Step 7 of 16

Fetch and pull: bring the changes home

Mia brings Sam’s fix down to her computer.

Do this, in GitHub Desktop

  1. Click Fetch origin to check for news
  2. It turns into Pull origin. Click it

What changed: Fetch only looks; Pull actually updates her folder. Everything matches again.

8

Step 8 of 16

Make a branch to try something

Mia wants to add a summary table, but she wants Sam to check it first. She works on a branch: a separate working version, so main stays untouched.

Do this, in GitHub Desktop

  1. Click Current Branch → New branch
  2. Name it add-table
  3. Click Create branch

What changed: Same folder, same files. Only the branch name changed. Anything she commits now goes to add-table, not main.

9

Step 9 of 16

Add the table, commit, publish the branch

Mia adds the table to notes.md, commits it to her branch, and publishes the branch.

Do this, in your folder

  1. Edit notes.md and save
  2. Commit with Summary Add summary table: the button now says Commit to add-table
  3. Click Publish branch

What changed: The branch is on GitHub.com too, but main there is still the version without the table.

10

Step 10 of 16

Open a pull request

Mia asks Sam to review the table. A pull request is a review page that shows exactly what the branch would change.

Do this, in GitHub.com

  1. Click Preview Pull Request, then Create pull request
  2. In the browser check base: main and compare: add-table
  3. Add a title and click Create pull request

What changed: Nothing in main has changed yet. A pull request is only a proposal.

11

Step 11 of 16

Review and merge

Sam does this

Sam reads Files changed, checks the numbers, and accepts the proposal by merging it.

Do this, in GitHub.com

  1. Sam opens the Files changed tab and reads every line
  2. He clicks Merge pull request, then Confirm merge

What changed: Now main on GitHub.com includes the table. Merging is the moment a change is accepted.

12

Step 12 of 16

Switch back to main and pull

Mia updates her own main so it has the accepted table.

Do this, in GitHub Desktop

  1. Click Current Branch → main
  2. Click Fetch origin, then Pull origin

What changed: Her folder’s main now matches the accepted version on GitHub.com.

Part 3: With an AI assistant

Let AI help, and check its work before you accept it.

13

Step 13 of 16

Give an AI assistant a small task

Mia asks an AI assistant connected to GitHub to write a data dictionary. She sets clear limits, and the AI opens its own pull request.

Do this, in GitHub.com

  1. Write the task as an Issue (Issues → New issue)
  2. Tell the AI: only add dictionary.md; don’t change notes.md; work on a new branch; don’t merge

What changed: The AI works on its own branch, agent/dictionary, so nothing reaches main without Mia’s review.

14

Step 14 of 16

Review the AI’s work, and catch a mistake

The AI says it’s done. Mia doesn’t take its word for it: she reads Files changed and spots that it also changed a number in notes.md, from 4.5% to 4.6%.

Do this, in GitHub.com

  1. Open Files changed and read every file
  2. Comment on the wrong line and choose Request changes

What changed: This is why AI work goes through a pull request. "Done" is a claim; the diff is the proof.

Watch out: Always check files the AI was told not to touch.

15

Step 15 of 16

Fixed, merged, pulled

The AI undoes its change to notes.md. Now only the new dictionary is in the pull request, so Mia merges it and pulls.

Do this, in your folder

  1. Check Files changed again: only dictionary.md
  2. Click Merge pull request → Confirm merge
  3. In Desktop: Fetch origin, then Pull origin

What changed: The dictionary is in her folder, and her numbers are untouched.

Part 4: When something goes wrong

Undo a mistake safely.

16

Step 16 of 16

Undo a mistake that was already pushed

While tidying up, Mia accidentally deletes the wage line, commits Tidy notes, and pushes. Sam already has it. She needs a safe undo.

Do this, in GitHub Desktop

  1. Open History and right-click Tidy notes
  2. Choose Revert changes in commit
  3. Click Push origin

What changed: Revert adds a new checkpoint that cancels the bad one. The line is back, and the history honestly shows what happened.

Watch out: Not pushed yet? Right after committing, the Undo button is simpler. Never "force push" to hide a shared mistake.

Four things people mix up

Commit is not push. Commit saves on your computer (step 3). Push puts it online (step 5).

Fetch is not pull. Fetch only checks for news. Pull brings it into your folder (step 7).

A pull request is not a merge. It’s a proposal (step 10). Merging accepts it (step 11).

"Done" is not proof. Read the AI’s changes yourself (step 14).

If something looks wrong

What you seeUsually meansDo this
GitHub.com shows the old fileYou committed but didn’t push, or the website shows another branchPush origin; check the branch on the website
Your folder shows the old fileSomeone changed it online (like step 6)Fetch origin, then Pull origin
Files "disappeared"You’re on a different branchCheck Current Branch before anything else
An AI says it’s done, but nothing changedIt worked on GitHub.com, or in another folderAsk for the pull request link
Desktop says there’s a conflictTwo people changed the same linesOpen the file, keep the right text, remove the <<<<<<< markers, save, then Continue merge

Never click Discard changes, delete branches, or "force push" just to make a message go away.
