Lesson 1 of 8, about 10 min

What is GitHub?

You'll learn: what GitHub does, the three places where your work lives, and the six words you'll see most. Time: 10 minutes. You need: nothing yet. Just read.

The problem GitHub solves

You're writing an economics paper. After a few weeks your folder looks like this:

paper_final.docx
paper_final_v2.docx
paper_final_v2_fixed.docx
paper_final_REALLY_final.docx

A coauthor fixed a table. An AI assistant rewrote a paragraph. Which file is right? What changed, and who approved it?

Illustration of a fictional project, not a screenshot.

GitHub keeps one project with a history of named checkpoints. You can look back at any earlier version, see exactly which lines changed, and decide whether to accept someone else's edit before it becomes the official version.

The three places your work lives

Every lesson in this guide uses these three places. Each has its own colour on the icons, so you always know where a step happens.

Place What it is What you do there
Your project folder Ordinary files on your computer Open and edit them with your usual editor
GitHub Desktop A free app for Mac and Windows See what changed, save checkpoints, upload and download
GitHub.com The shared online copy View files, discuss tasks, review and accept changes

You never type commands. GitHub Desktop has buttons for everything in this guide.

Six words you'll see everywhere

Word Plain meaning Example
Repository (repo) A project folder that remembers its history All files for one paper
Changes What's different since your last checkpoint You edited one paragraph
Commit Save a named checkpoint, on your computer "Explain wage units in table 1"
Push Upload your checkpoints to GitHub.com Share your updated notes
Pull Download changes from GitHub.com to your folder Get a coauthor's corrections
Branch A separate working version for trying things Test a new specification safely

The one rule to remember: commit saves on your computer; push puts it online. Until you push, nobody else can see your checkpoint.

When is GitHub a good idea?

Situation Use GitHub?
Revising notes, Markdown, LaTeX, R or Python files over weeks Yes. You'll see every change.
A coauthor or an AI assistant proposes edits you want to check first Yes. Review pages were made for this.
Writing together at the same moment, like in Google Docs Not ideal. A shared document editor is easier.
Word files and PDFs Works, but GitHub can't show what changed inside them.
Confidential data, student records, passwords No, unless your institution has approved it.

See a real example (nothing to install)

This repository contains a tiny, made-up economics project with real GitHub records you can click:

  1. The first saved version: a checkpoint of the original files.
  2. Issue #3: a written task asking for variable definitions and a calculation check.
  3. Pull Request #4, Files changed: the proposed edits, line by line, before they were accepted.

The counties and numbers are fictional. The GitHub records are real.

Check yourself

You clicked Commit. Can your coauthor see your change yet?

No. A commit is saved on your computer only. You need to Push before it appears on GitHub.com.

Where do you actually edit a file: GitHub Desktop or your editor?

Your editor (for example TextEdit, Notepad, Word or VS Code). GitHub Desktop shows and saves the changes; it isn't where you type.

Lesson 2 of 8, about 10 min

Get set up

You'll learn: how to make a GitHub account, install GitHub Desktop, and connect the two. Time: 10 minutes. You need: an email address and a Mac or Windows computer.

Steps

Step 1: Create a free GitHub account

On GitHub.com

Do this: go to github.com/signup, enter your email, choose a password and a username, and confirm your email address.

You'll see: your GitHub.com home page, with your username in the top-right corner.

Watch out: Your username appears on everything you share. Pick one you're happy for coauthors to see.

Step 2: Install GitHub Desktop

In GitHub Desktop

Do this: download the app from desktop.github.com and open it.

  • Mac: open the downloaded file and drag GitHub Desktop into Applications.
  • Windows: run the downloaded installer; the app opens when it's done.

You'll see: a welcome screen.

Watch out: You don't need to install "Git" separately or open a terminal. GitHub Desktop includes everything.

Step 3: Sign in to GitHub Desktop

In GitHub Desktop

Do this: on the welcome screen, click Sign in to GitHub.com. Your browser opens; approve the request, then return to the app.

If you skipped the welcome screen, open the settings instead:

  • Mac: GitHub Desktop → Settings… → Accounts → Sign in
  • Windows: File → Options… → Accounts → Sign in

You'll see: your GitHub username listed under Accounts.

Step 4: Choose a text editor (optional)

In GitHub Desktop

Do this: in the same settings window, open Integrations and pick an External Editor if you have one, such as Visual Studio Code. If you don't, that's fine: you can always open files from the folder with TextEdit (Mac) or Notepad (Windows).

You'll see: later, the menu item Repository → Open in your editor opens your whole project in one click.

Watch out: On a Mac, TextEdit sometimes saves as "rich text". Choose Format → Make Plain Text before editing .md files.

You're ready

Place Status
GitHub.com You have an account
GitHub Desktop Installed and signed in
Your project folder Created in the next lesson

Check yourself

Do you need to learn command-line Git to use this guide?

No. Every step in this guide uses buttons in GitHub Desktop or on GitHub.com.

Lesson 3 of 8, about 15 min

Your first project

You'll learn: to create a project, change one file, save a checkpoint, and see it online. This is the whole GitHub idea in six steps. Time: 15 minutes. You need: Lesson 2 done.

The route for this lesson. Follow the line: it starts in GitHub Desktop, visits your folder to edit a file, and ends on GitHub.com.

Practise on your own new project, not on someone else's shared project. Then nothing you try can affect anyone else.

Steps

Step 1: Create a repository

In GitHub Desktop

Do this: choose File → New repository… and fill in:

Field Type or choose
Name my-first-notes
Description My practice project
Local path A folder you'll remember, such as Documents
Initialize this repository with a README Tick it
Git ignore, License Leave as they are

Click Create repository.

You'll see: my-first-notes under Current Repository at the top left. The Changes tab says there are no local changes.

Simplified drawing, not a screenshot. Buttons may sit in slightly different places in your version.

Step 2: Edit one file

In your project folder

Do this: choose Repository → Show in Finder (Mac) or Repository → Show in Explorer (Windows). Open README.md in your text editor, replace its text with this, and save:

# My First Notes

This is my practice project.

- Today I learned how to save a checkpoint.
- Next I want to try a branch.

You'll see: nothing changes in GitHub Desktop until you save.

Watch out: Edit the file inside the folder Desktop just opened, not a copy in Downloads.

Step 3: Review your change

In GitHub Desktop

Do this: go back to GitHub Desktop. Click the Changes tab, then click README.md.

You'll see: added lines in green with a +, removed lines in red with a −. This view is called the diff.

Watch out: File not listed? You probably haven't saved yet, or you saved it somewhere else.

Step 4: Commit (save a checkpoint)

In GitHub Desktop

Do this: in the Summary box at the bottom left, type Add my first notes. Click Commit to main.

You'll see: the Changes list empties. Your checkpoint appears in the History tab.

Watch out: The checkpoint is saved on your computer only. It isn't online yet.

Step 5: Publish to GitHub.com

In GitHub Desktop

Do this: click Publish repository in the top bar. Leave Keep this code private ticked. Click Publish repository.

You'll see: the top-bar button changes to Fetch origin. That means your project is now connected to GitHub.com.

Watch out: A public project can be seen by anyone on the internet. Keep practice projects private.

Step 6: Check it online

On GitHub.com

Do this: choose Repository → View on GitHub.

You'll see: your browser shows my-first-notes with the text you wrote.

You did it

You've used all three places: you edited in your folder, committed and published in GitHub Desktop, and checked on GitHub.com. Every other workflow in this guide is a variation of this one.

Check yourself

What's the difference between the Changes tab and the History tab?

Changes shows edits you haven't committed yet. History shows checkpoints you've already committed.

You make a second edit tomorrow. Which buttons do you use?

Save the file, then in Desktop: review Changes, Commit to main, then Push origin. (Lesson 4 covers this.)

Try it in the simulator

Want to rehearse before touching the real app? The interactive course lets you click through these same steps on a safe, pretend version of GitHub Desktop.

Lesson 4 of 8, about 10 min

Save and sync every day

You'll learn: the two routines you'll use most: sending your changes up, and bringing other people's changes down. Time: 10 minutes. You need: a published project from Lesson 3.

Part A: Send your changes up

Your everyday routine: edit in your folder, commit and push in Desktop.

Step 1: Check where you are

In GitHub Desktop

Do this: look at the top bar: Current Repository and Current Branch.

You'll see: your project name and a branch name, usually main.

Watch out: Most "where did my file go?" moments start with the wrong project or branch selected.

Step 2: Edit and save

In your project folder

Do this: open the project (Repository → Open in your editor, or Show in Finder / Show in Explorer), make your change, and save.

Step 3: Review your changes

In GitHub Desktop

Do this: click Changes. Read each file's diff. Untick any file you don't want in this checkpoint.

You'll see: only ticked files go into the commit.

Watch out: Look for surprises: deleted files, files you didn't mean to touch, or passwords.

Step 4: Commit

In GitHub Desktop

Do this: write a Summary that says what changed, for example Clarify wage units in table 1, and click Commit to main.

You'll see: the top bar now shows Push origin with a small number: the checkpoints waiting to upload.

Step 5: Push origin

In GitHub Desktop

Do this: click Push origin.

You'll see: the number disappears. Your checkpoint is on GitHub.com.

Step 6: Confirm online (optional)

On GitHub.com

Do this: Repository → View on GitHub, then refresh.

Watch out: Still old? Check the branch selector on the website matches the branch you pushed.

Part B: Bring other people's changes down

When the online copy changed, the route goes the other way: from GitHub.com, through Desktop, into your folder.

Your folder does not update by itself. When a coauthor, an AI assistant, or you on another computer changes the project online, you bring it down like this:

Step 1: Finish your own edits first

In GitHub Desktop

Do this: look at Changes. If you have unfinished edits, commit them before you continue.

Watch out: Never click Discard changes just to make a message go away. It deletes unsaved work.

Step 2: Choose the branch

In GitHub Desktop

Do this: Current Branch → main (or whichever branch changed).

Step 3: Fetch origin

In GitHub Desktop

Do this: click Fetch origin.

You'll see: if there's anything new, the button becomes Pull origin with a number.

Fetch only looks. It doesn't change your files yet.

Step 4: Pull origin

In GitHub Desktop

Do this: click Pull origin.

You'll see: new checkpoints in History, and updated files in your folder.

Watch out: If Desktop says there's a conflict, stop and read Lesson 8.

Looking back in time

Use History to see older versions

In GitHub Desktop

Do this: click the History tab, then click any checkpoint.

You'll see: who saved it, when, the Summary, and exactly which lines changed.

This is how you answer "which version of table 2 did we submit?" without filenames like table2_final_v3.

The two-line summary

When Click
You changed something Commit → Push origin
Someone else changed something Fetch origin → Pull origin

Check yourself

What's the difference between Fetch and Pull?

Fetch checks GitHub.com for anything new. Pull actually brings it into your folder.

You pushed, but the website shows the old file. What do you check?

That the website is showing the same branch you pushed, and that you refreshed the page.

Lesson 5 of 8, about 20 min

Branches and pull requests

You'll learn: how to try a change without touching the accepted version, then have it reviewed before it's accepted. Time: 20 minutes. You need: your project from Lesson 3.

Why bother?

Your paper's main version is correct. You want to try a different set of control variables, but if it doesn't work out, you don't want to undo a mess.

  • A branch is a separate working version. Edits there don't touch main.
  • A pull request (PR) is a review page on GitHub.com. It shows exactly what your branch would change in main, so you or a coauthor can check it.
  • Merge means accepting the pull request. Only then does main change.
main  ●────────●────────────────●   accepted version
                \              /
robustness/      ●────●────●──    your experiment, reviewed, then merged
new-controls

The route for this lesson. Notice the middle part: the review happens on GitHub.com before anything reaches main.

Steps

Step 1: Start from the latest main

In GitHub Desktop

Do this: Current Branch → main, then Fetch origin, and Pull origin if it appears.

You'll see: an up-to-date main, so your branch starts from the newest version.

Step 2: Create a branch

In GitHub Desktop

Do this: Current Branch → New branch. Name it after what you're trying, such as robustness/new-controls. Click Create branch.

You'll see: the top bar shows your new branch. Your files look the same; nothing has changed yet.

Watch out: A branch is not a copy of your folder. The same folder now shows the branch's version of the files.

Step 3: Edit and save

In your project folder

Do this: make your change in your editor and save.

Step 4: Commit to your branch

In GitHub Desktop

Do this: review Changes, write a Summary, and click Commit to robustness/new-controls.

You'll see: the button names your branch, not main. That's how you know main is safe.

Step 5: Publish the branch

In GitHub Desktop

Do this: click Publish branch in the top bar.

You'll see: the branch now exists on GitHub.com too.

Step 6: Open a pull request

On GitHub.com

Do this: in Desktop, click Preview Pull Request, then Create pull request. Your browser opens. Check the two branch boxes at the top:

Box Means Should say
base the version you want to change main
compare the branch with your proposal robustness/new-controls

Add a title and a short description of what you changed and why, then click Create pull request.

You'll see: a review page with the tabs Conversation, Commits and Files changed.

Watch out: Not finished yet? Use the arrow next to the button and choose Create draft pull request.

Step 7: Review the changes

On GitHub.com

Do this: open Files changed and read every file. You or a reviewer can click any line to leave a comment.

You'll see: exactly what was added (green) and removed (red).

Watch out: You might see a Checks area. Those are automatic tests some projects set up. If your project has none, that's normal.

Step 8: Merge

On GitHub.com

Do this: when it's right, click Merge pull request, then Confirm merge.

You'll see: the pull request is marked Merged. main on GitHub.com now includes your change.

Watch out: Merging is the moment of acceptance. Only merge after you've read the changes.

Step 9: Bring main home

In GitHub Desktop

Do this: Current Branch → main, then Fetch origin and Pull origin.

You'll see: your folder's main now includes the accepted change.

A real pull request to look at

Pull Request #4 in this repository proposed four documentation files for a made-up economics dataset. Open Files changed and notice that the data file itself was not touched. That's what a well-scoped PR looks like.

Check yourself

You opened a pull request. Has main changed?

No. A pull request is only a proposal. main changes when someone clicks Merge.

Your experiment failed. What happens to main?

Nothing. Close the pull request without merging (or never open one), and switch back to main.

Lesson 6 of 8, about 20 min

Work with other people

You'll learn: how to join a coauthor's project, write tasks as Issues, and get your work reviewed. Time: 20 minutes. You need: Lesson 5, and a coauthor's project (or a friend willing to try).

The route for joining someone's project. Dashed stations are steps your teammate does.

Steps

Step 1: Get access

Done by your teammate, on GitHub.com

Do this: ask the project's owner to add you. On GitHub.com they open the project's Settings → Collaborators, click Add people and type your username. You accept the invitation from your email or from GitHub notifications.

You'll see: the project in your list on GitHub.com.

Watch out: Without access you can still read and copy a public project, but you can't upload to it.

Step 2: Clone the project

In GitHub Desktop

Do this: File → Clone repository…, choose the GitHub.com tab, select the project, pick a local folder, and click Clone.

You'll see: a connected copy of the project in your folder, and its name under Current Repository.

Watch out: Clone once. Afterwards, use Fetch and Pull to get updates. Don't use Download ZIP: a ZIP copy isn't connected and can't sync.

Step 3: Create your own branch

In GitHub Desktop

Do this: Current Branch → New branch, for example docs/fix-variable-definitions.

Step 4: Edit and save

In your project folder

Do this: make your change in your editor and save.

Step 5: Commit and publish

In GitHub Desktop

Do this: review Changes, click Commit to your branch, then Publish branch.

Step 6: Open a pull request and ask for a review

On GitHub.com

Do this: Preview Pull Request → Create pull request. On the pull request page, use Reviewers on the right to request your teammate.

You'll see: your teammate gets a notification.

Step 7: Your teammate comments

Done by your teammate, on GitHub.com

Do this: nothing. Your teammate reads Files changed and comments, approves or requests changes.

Step 8: Fix and push again

In GitHub Desktop

Do this: stay on the same branch. Edit, commit, and click Push origin.

You'll see: the same pull request updates automatically. Don't open a new one.

Step 9: Your teammate merges

Done by your teammate, on GitHub.com

Do this: when you both agree, the owner clicks Merge pull request.

Step 10: Update your main

In GitHub Desktop

Do this: Current Branch → main, Fetch origin, Pull origin.

Write tasks as Issues

An Issue is a written to-do on GitHub.com

On GitHub.com

Instead of an email saying "please fix the dataset", open the project's Issues tab, click New issue, and write:

  • What's needed: "Say whether the unemployment change is in percent or percentage points."
  • Which files: draft_results.md only.
  • How we'll know it's done: the table says "percentage points" and the arithmetic is shown.

Everyone can see the task, discuss it in one place, and link the pull request that fixes it. A real example: Issue #3 led to Pull Request #4.

Good habits for shared projects

Habit Why
Pull before you start You begin from everyone's latest work
One branch per task Reviews stay small and clear
Small, clearly named commits History explains itself: "Fix wage units", not "stuff"
Nobody merges their own work unreviewed A second pair of eyes catches mistakes
Two people editing the same paragraph? Talk first Overlapping edits cause conflicts (Lesson 8)

Check yourself

Your teammate asked for changes. Do you open a new pull request?

No. Push new commits to the same branch; the existing pull request updates by itself.

Why clone instead of downloading a ZIP?

A clone stays connected to GitHub.com, so you can Push and Pull. A ZIP is a disconnected copy.

Lesson 7 of 8, about 20 min

Work with an AI assistant

You'll learn: how to let an AI assistant help with your project while you stay in control of what's accepted. Time: 20 minutes. You need: Lesson 5 (branches and pull requests).

The one idea

The AI proposes; you review; you decide. Treat an AI assistant like a new coauthor: give it a small, clear task, keep its work on a separate branch, and read every change before you accept it.

Which kind of assistant do you have?

Your assistant… Where its work appears Follow
Can only chat Nowhere, until you paste its text into a file yourself Part C
Edits files on your computer (for example, an AI-enabled editor) GitHub Desktop Changes Part A
Works on GitHub.com and opens pull requests A pull request on GitHub.com Part B

Not sure? Ask it: "Can you edit files in my project, and where?" If it can't show you a changed file or a pull request link, treat it as chat-only.

Part A: An assistant that edits your folder

Local AI route. The dashed station is the step the AI does; every other step is you checking and accepting.

Step 1: Make a branch for the AI

In GitHub Desktop

Do this: pull the latest main, then Current Branch → New branch, for example agent/data-dictionary.

You'll see: main is now protected from the AI's edits.

Step 2: Point the AI at the exact folder and give a small task

In your project folder

Do this: use Repository → Show in Finder / Show in Explorer to find the folder, and open that same folder in your AI tool. Then give it a task with clear limits (see the instruction to copy, below).

Watch out: Ask the AI to tell you its folder and branch before it edits. If it names a different folder, stop: it's working on another copy.

Step 3: The AI edits

Done by the AI assistant

Do this: let it work. Ask it not to commit or push, so you can review first.

Step 4: Review every change

In GitHub Desktop

Do this: open Changes and click through every file.

You'll see: only the files you allowed.

Watch out: Look for deleted files, renamed files, changed data, or numbers it invented. If the AI already committed, look in History instead.

Step 5: Check the result yourself

In your project folder

Do this: open the edited file and read it. Recheck any numbers and click any links.

Watch out: "Done" from an AI is a claim, not proof.

Step 6: Commit, publish, and accept through a pull request

In GitHub Desktop

Do this: Commit to agent/data-dictionary, Publish branch, then Preview Pull Request → Create pull request. Read Files changed once more, merge, and pull main (as in Lesson 5).

Part B: An assistant that works on GitHub.com

Cloud AI route. Almost everything happens on GitHub.com; your folder only changes when you pull at the end.

Some assistants connect to GitHub and open pull requests by themselves. What's available depends on the product, your plan and the project's permissions.

Step 1: Write a clear Issue

On GitHub.com

Do this: Issues → New issue. Describe one goal, which files it may change, what it must not change (for example the data file and main), and how you'll check the result.

Step 2: The AI opens a pull request

Done by the AI assistant

Do this: assign the Issue to the AI if your service supports that, or ask your connected assistant to work on a new branch and open a draft pull request.

Watch out: Never ask an AI to merge its own work or to change main directly.

Step 3: Check the pull request really exists

On GitHub.com

Do this: open Pull requests, find it, and read Files changed for every file.

Watch out: No pull request link means nothing to review yet, whatever the chat says.

Step 4: Look at it on your computer (optional)

In GitHub Desktop

Do this: in Desktop, Current Branch → Pull Requests, pick the AI's pull request, and open the files in your editor.

Step 5: Ask for fixes, or merge

On GitHub.com

Do this: comment with exact file names and what to change. When it's right, Merge pull request.

Step 6: Update your folder

In GitHub Desktop

Do this: Current Branch → main, Fetch origin, Pull origin. The AI's work never appears in your folder until you pull.

Part C: A chat-only assistant

Paste, review, commit

In your project folder

Do this: ask for the text, paste it into your file, save, then review it in Desktop's Changes and commit it yourself, exactly as in Lesson 4.

An instruction you can copy

Please add a short data dictionary explaining my variables and their units. Only edit data_dictionary.md. Do not change the CSV or main. Work on the branch agent/data-dictionary if you can edit files. Tell me exactly which files you changed and what you checked. Do not merge anything. If you can't edit files, give me the text to paste myself.

More ready-made instructions: AI prompt library.

Before you merge an AI's work

Check Look at
Only the files you allowed changed Desktop Changes, or Files changed on the PR
Nothing important was deleted or renamed The file list in the diff
The numbers and facts are right Open the files and recheck them yourself
No passwords or private data were added The diff
You, not the AI, click Merge The pull request page

A real example

In this repository, Issue #3 asked for variable definitions and a check of two calculations in a made-up economics dataset. An AI assistant (ChatGPT, using authorized GitHub tools) opened Pull Request #4, which a human reviewed and merged. Notice in Files changed that four documentation files changed and the data file did not, and that the results describe 5.0% → 4.5% as 0.5 percentage points, not 0.5%.

Check yourself

The AI says "All done!" but Desktop shows no changes. What now?

Ask for evidence: which folder, which branch, which pull request link. A cloud assistant's work appears as a pull request on GitHub.com, not in your folder.

Lesson 8 of 8, about 15 min

Fix mistakes

You'll learn: how to undo safely at each stage, and what to check when something looks missing. Time: 15 minutes. Use it: whenever something goes wrong.

First rule: don't panic-click Discard, delete branches, or follow advice to "force push". Find out where you are first.

The recovery route. Work down it and stop at the first step that matches your situation.

Steps

Step 1: Find out where you are

In GitHub Desktop

Do this: check Current Repository, Current Branch, the Changes tab and the History tab.

You'll see: whether your change is unsaved (in Changes), committed (in History), pushed (no Push origin number), or merged (on GitHub.com).

Watch out: Many "lost" files are just on another branch. Switch back before assuming anything was deleted.

Step 2: An unwanted edit you haven't committed

In GitHub Desktop

Do this: in Changes, click the file and read what would be lost. Copy anything you want to keep. Then right-click the file and choose Discard changes…

You'll see: the file returns to its last checkpoint.

Watch out: Discarding can't easily be undone. If you're unsure, copy the whole folder somewhere safe first.

Step 3: You just committed, but haven't pushed

In GitHub Desktop

Do this: right after committing, GitHub Desktop shows an Undo button below the commit box. Click it.

You'll see: your edits are back in Changes, uncommitted, ready to fix.

Watch out: Only undo checkpoints you haven't pushed.

Step 4: The mistake is already pushed or merged

In GitHub Desktop

Do this: in History, right-click the commit and choose Revert changes in commit. Then click Push origin.

You'll see: a new checkpoint that cancels the old one. The history stays honest: everyone can see what happened and why.

Watch out: Never force-push or delete shared branches to hide a mistake.

Step 5: Two edits clash (merge conflict)

In your project folder

Do this: if Desktop lists conflicted files, click Open in your editor. You'll see both versions between marker lines like <<<<<<<, ======= and >>>>>>>. Keep the right text, delete the marker lines, and save. Back in Desktop, click Continue merge.

You'll see: the conflict list empties and the merge finishes.

Watch out: Don't assume your version (or the AI's) should win. Ask the person who wrote the other version.

"I can't see my changes"

What you see Most likely reason Do this
GitHub.com shows the old file You committed but didn't push, or you're viewing another branch Push origin; check the branch selector on the website
Your folder shows the old file Someone changed it online Fetch origin → Pull origin on the right branch
An AI says it finished, but nothing changed It worked on GitHub.com, or on a different folder Ask for the pull request link or the folder path
Files "disappeared" after switching branches That branch has a different version Switch back with Current Branch
Desktop doesn't know about your folder It's a ZIP download, not a clone File → Clone repository… once, then work there

"Push was rejected" or "permission denied"

  • Check you're signed into the right account (Desktop settings → Accounts).
  • You may not have write access. Ask the owner, or open a pull request instead.
  • The online branch may have newer commits. Click Fetch origin, then Pull origin, then push again.
  • A very large file can be refused. Keep big datasets outside the repository.

Before you share anything

Check
No passwords, keys, private data or student records
No unexpected deletions or unrelated edits
Right project, right branch
The full diff has been read

Check yourself

You pushed a wrong number to main yesterday. Undo or Revert?

Revert. Undo is only for the commit you just made and haven't pushed.

Practise everything

Four short labs that repeat the lessons with your own hands. Use your own practice project (from Lesson 3) and nothing private.

Warm-up: inspect a real example (no clicking needed)

Open Find

The accepted results Check the arithmetic: 5.0% → 4.5% is −0.5 percentage points; $25 → $26 is +4.0%

The example project's files are in examples/economics. The counties and numbers are invented.

Lab 1: Branch and commit (10 minutes)

Goal: make a change on a branch and see that main stays untouched.

  1. Current Branch → New branch: practice/lab-1-note.
  2. In your folder, create my-practice-note.md with a heading and three bullet points. Save.
  3. In Desktop, look at Changes, then Commit to practice/lab-1-note.
  4. Click Publish branch.
  5. On GitHub.com, use the branch selector to view practice/lab-1-note, then main.

Done when: the file is on your branch and not on main.

Lab 2: Pull request and merge (10 minutes)

Goal: accept a change through review.

  1. In Desktop, Preview Pull Request → Create pull request.
  2. Check base: main and compare: practice/lab-1-note.
  3. Create it, then read Files changed.
  4. Click Merge pull request → Confirm merge.
  5. In Desktop, Current Branch → main → Fetch origin → Pull origin.

Done when: my-practice-note.md is in your folder while on main.

Lab 3: An AI assistant's proposal (15 minutes)

Goal: review an AI's work like a coauthor's.

  1. Create the branch agent/lab-3-note.
  2. Ask any AI assistant: "Add one short paragraph to my-practice-note.md explaining Commit versus Push. Keep the three bullets. Don't change other files. If you can't edit files, give me the text to paste."
  3. Apply the change (or let the AI edit, if it can reach your folder).
  4. In Desktop Changes, confirm only that one file changed and nothing was removed.
  5. Commit, publish, open a pull request, read Files changed, merge.

Done when: you can say exactly what the AI changed, and what you checked yourself.

Lab 4: Break it and fix it (10 minutes)

Goal: practise recovery without fear.

  1. On main, delete one bullet from your note, commit, and push.
  2. In History, right-click that commit → Revert changes in commit, then Push origin.
  3. Edit the note again but don't commit. Right-click it in Changes → Discard changes…

Done when: the bullet is back and History shows both the mistake and the revert.

AI prompt library

Show

Ready-made instructions for working with an AI assistant on a GitHub project. Replace the words in CAPITALS. These are templates, not guarantees: what an assistant can actually do depends on the product and the access you give it. New to this? Read Lesson 7 first.

1. Look first, change nothing

Use when: starting with an unfamiliar project.

Review the repository OWNER/REPO. Summarize what each folder and important file is for, and list unclear text or broken links. Do not make any edits. Recommend changes in order of importance, and say what you couldn't check.

2. One small, controlled edit

Use when: you want one specific improvement.

Work in OWNER/REPO on a new branch agent/TASK. Goal: ONE-SENTENCE OUTCOME. Only edit FILES. Do not change main, delete other files, or change settings. Keep existing useful content. Tell me exactly which files you changed and what you checked. Do not merge. If you can't edit the repository, give me a complete draft to paste.

3. Edit my local folder, but let me review before saving

Use when: the assistant can edit files on your computer.

Before editing, tell me the full folder path and the current branch. Stop if they aren't EXPECTED-FOLDER and agent/TASK. Edit only FILES to GOAL. Don't commit, push, switch branches or delete files. When finished, list the changes so I can review them in GitHub Desktop.

4. Work on GitHub.com and open a pull request

Use when: the assistant is connected to GitHub and can open pull requests.

Complete Issue #NUMBER in OWNER/REPO. Use a new branch agent/TASK. Don't change main, force-push, or merge. Only change PATHS. Open a draft pull request into main describing what changed, what you checked, and what still needs a human decision. Don't claim success unless I can see the pull request.

5. Second opinion on a pull request

Use when: you want a review before you merge.

Review the pull request at URL against its Issue. Look for wrong files, unexpected deletions, broken links, inconsistent terms and claims that aren't supported. Sort findings into must fix, nice to have and couldn't check, with file names. Don't edit, approve or merge anything.

6. Improve one section only

Use when: polishing writing without a rewrite.

In OWNER/REPO, improve only the section HEADING in FILE. Keep all numbers, equations, links and examples unless they're clearly wrong. Write for a beginner in short sentences. Don't add new sections. Show me a before/after summary.

7. Handover note for the next session

Use when: pausing work or moving to a new chat.

Write a short handover: goal, repository and branch, files looked at, files changed, checks done, open questions, and the exact next step. Label anything you didn't verify. Don't describe suggested changes as saved unless you've confirmed the commit.

8. Explain a deletion before I accept it

Use when: a pull request removes files.

The pull request at URL removes FILES. For each one, was the removal requested? Could it break links or anything else? What's the safest way to restore it if needed? Read only; don't change the repository.

Add this line when it matters

Show proof, not claims: name the branch and every file changed; separate what you changed from what you only suggested; say which checks passed, failed or weren't run. No private data, no passwords, no deleting files, no changes to main.
